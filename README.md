# Healthcare appointments: Warangal and Hanamkonda

A Vite/React appointment application with Supabase authentication and database support. The public hospital directory is sourced separately from clinician schedules. A directory listing does not mean a hospital participates in this service.

## Run locally

Use Node.js 22 or later. Run `npm ci`, then `npm run dev`. Create local frontend environment variables following the application configuration: `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`. Only the public anon key belongs in the browser. Never put a service-role key in a VITE_ variable, frontend file, commit, or screenshot.

Run `npm run build` for a production build and `node --test scripts/sync-hospitals.test.mjs` for directory validation and failed-request preservation tests. CI runs npm ci, these tests, and the Vite build on pushes and pull requests.

Database setup, authentication, role policies, booking constraints, and administrator bootstrap are documented in [supabase/README.md](supabase/README.md). Complete that setup before treating a booking as persisted. Hospital directory data alone does not create doctor accounts, specialties, approved schedules, or appointment availability.

## Hospital sources and limits

`public/hospitals.json` is an array of records with stable UUID `id`, `name`, `city` (Warangal or Hanamkonda), `address`, `source_url`, empty `specializations`, and `last_verified_at`. Specializations, doctors, and appointment slots are never inferred from names or generated by the data updater.

The government baseline contains MGM Warangal, CKM Warangal, and Regional Eye Hospital with addresses from the [Warangal district health directory](https://warangal.telangana.gov.in/health/), reviewed on 2026-11-13. These entries retain that date-only review value and their government source. Fetching OSM does not re-verify the government entries. A review date is not a hospital affiliation or a clinical endorsement.

Additional listings come from OpenStreetMap's public Overpass API. Attribution: © [OpenStreetMap contributors](https://www.openstreetmap.org/copyright), available under the Open Database License (ODbL). Each OSM listing links directly to its source object. Retain this attribution in public displays and comply with ODbL for database reuse.

The query only requests `amenity=hospital` nodes, ways and relations within latitude 17.93–18.05 and longitude 79.48–79.67. This is a deliberately bounded urban study area, not either district's full boundary. The script independently checks returned coordinates, hospital facility type, name and city. City evidence must be an explicit `addr:city` equal to Warangal, Hanamkonda or Hanumakonda, or an explicit city name in `addr:full` at the end (optionally followed by Warangal, Telangana or a postcode) or followed by a comma and a landmark introduced with near/opposite/beside. The latter spelling is normalized to Hanamkonda. Nearby-city, highway-only, district and mandal descriptions are not city evidence; conflicting city tags are excluded. Cities are never guessed from coordinates, hospital names or postcodes. Obvious clinic/optical/diagnostic names and conflicting healthcare facility tags are excluded even if mislabeled as hospitals. As a result the list is incomplete, especially for poorly tagged facilities.

For OSM entries, `last_verified_at` is the actual successful API fetch/check timestamp, not the object's edit time and not a phone or on-site verification. OSM can be outdated or incorrect. Patients should confirm location and services with the hospital.

## Automatic daily updates

Run `node scripts/sync-hospitals.mjs` manually. It tries three public Overpass endpoints, validates the complete response, merges eligible OSM listings with the independent government baseline, and atomically replaces the public snapshot. API errors, invalid or partial payloads, and zero eligible results fail with nonzero status and leave the snapshot unchanged. Existing OSM timestamps remain old after failure; no success timestamp is fabricated. A source-fetch check does not confirm that a facility is open.

The GitHub workflow [update-hospitals.yml](.github/workflows/update-hospitals.yml) runs at 00:30 UTC (06:00 IST) daily and supports **Run workflow**. GitHub schedules may run late and may need re-enabling after repository inactivity. The workflow has only contents-write permission, runs the safety tests, then commits only the hospital JSON when the sync succeeds. Review failed Actions runs; the app does not promise a successful refresh every day. When bootstrapping, only the government baseline may be present until a live fetch succeeds.

Optional server-side database synchronization uses GitHub repository Actions secrets `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` together. Without both configured, the public-file update remains usable without database synchronization; configuring only one is an error. The script POSTs an upsert to `/rest/v1/hospitals?on_conflict=id` using the documented record fields. It does not delete absent database records, alter clinician-managed data, or insert appointments. A database error fails the job before the local snapshot is replaced. The operation is idempotent; review stale database entries separately. Supabase must have a compatible hospitals table and columns before enabling these secrets. Do not use browser-local secrets for this task.

## Deploy with GitHub and Vercel

1. Create a GitHub repository and commit the project, including `.github/workflows/`, `public/hospitals.json`, and the lockfile. Ordinary browser uploads may reject hidden workflow paths or lack the required workflow permission. If so, use Git/GitHub Desktop or the GitHub editor with the correct repository authorization; do not silently omit the workflows.
2. Import that repository in Vercel, select the Vite preset, build command `npm run build` and output directory `dist`. Add only public frontend Supabase URL/anon-key environment variables to Vercel. Authorize the repository integration and use the intended production branch.
3. Apply Supabase setup and set the authentication Site URL and allowed redirect URLs to the production HTTPS domain. Redeploy after changing frontend environment variables.
4. Enable Actions and repository workflow write access. Run **Update hospital directory** manually and inspect its run and data commit. If branch protections reject the push, use an approved bot/branch policy instead of disabling protection without review.
5. Confirm that Vercel creates a deployment for the data commit and that the production directory shows the new source-check dates. GitHub-to-Vercel integration and author/repository access must permit automated commits. A generated JSON commit without a successful Vercel deployment does not refresh the public site. Check integration configuration if no deployment appears.

`vercel.json` configures Vite output, SPA fallback for extensionless routes, short hospital-JSON caching, and security headers. No CSP is imposed that would inadvertently block Supabase requests. Add a tested restrictive CSP before production. No paid service is required by this setup, but free plans have quotas and availability limits; monitor them and verify current eligibility. Scheduled updates stop if the repository, workflow, provider, or deployment integration is unavailable.

## Before accepting real patients

This repository is a starting point, not a medical-service launch approval. Keep demo activity separate from real patient data until these checks are complete:

- Obtain hospital participation/consent and independently verify clinicians' identities, registrations, specialties and approved schedules. Confirm the operational process for booking acceptance, cancellation and patient communication. A sourced directory entry is not consent to accept bookings.
- Configure confirmed-email authentication, a production email/SMTP provider, sender identity, password-reset flows, rate limits and abuse protection. Check delivery rather than relying on a development email quota. Availability of a free SMTP tier is not guaranteed.
- Test row-level security and server-side authorization with two patients, clinician and admin accounts, including direct API attempts, revoked sessions and role escalation. Prove that patients cannot read others' appointments and clinicians cannot access unrelated records. Test duplicate/concurrent booking, cancellation, time zones and stale-slot behavior.
- Document lawful basis/consent, privacy notices, data minimization, retention/deletion, patient rights, access logging and incident response under applicable Indian privacy/health obligations. Obtain qualified legal/security review; this project does not certify compliance. Do not put diagnoses, medical documents or unnecessary sensitive data into appointment notes.
- Test database backups and restoration, secrets rotation, monitoring/alerts, audit trails, downtime handling and a contact channel for booking failures. Free-tier backups/retention may be insufficient; arrange an appropriate recovery process before launch.
- Run accessibility, mobile, dependency, application-security and end-to-end tests against the deployed environment. A successful build or directory-sync test does not establish patient safety or production readiness.

**Not for emergencies.** Do not use this application for urgent symptoms or emergency dispatch. Seek immediate local emergency care instead. Appointment submission must never be presented as guaranteed care or emergency assistance.

## Coverage audit and known gaps (2026-11-13)

The requested scope is all discoverable hospitals in Warangal and Hanamkonda, not just the initial three public hospitals. This directory is **not an exhaustive or authoritative register**. It combines the Warangal health-directory baseline, the [Hanumakonda government-hospitals page](https://hanumakonda.telangana.gov.in/public-utility-category/govthospitals/) (four names; three overlap the baseline), and every eligible result from the bounded OSM query. The Hanumakonda page labels Govt Maternity Hospital as Warangal but supplies no street address; its address field intentionally contains only that sourced city. The district site header is not used to infer Hanamkonda city.

The Warangal health page's reference to 228 district registered institutions is not a list of 228 twin-city hospitals: it includes a wider district and institution types. A complete current registered-hospital list with city addresses was not obtained. Getting the current DMHO/health-department register for both districts, filtering it to the twin cities and reconciling duplicates is an outstanding coverage task. Facilities without an explicit city in OSM address data remain excluded. OSM can misclassify facilities and this pipeline cannot establish clinical licensing.

The live bounded OSM response obtained on 2026-11-13 contained 182 facility objects before name, address, type, boundary and duplicate validation. That is not a count of verified hospitals. Private-hospital sources are not silently promoted from snippets: the Rohini official page failed certificate validation in the research browser, and a previous Ajara contact-page extraction timed out. Neither failure is evidence that a hospital does not exist; these are gaps for later direct-source verification. Rohini is still eligible if independently present with an explicit Hanamkonda address in OSM, with OSM attribution rather than unverified website claims.

The checked public snapshot currently contains **57 sourced listings: 8 Warangal and 49 Hanamkonda** (4 government-source entries plus 53 OSM entries). OSM checked at 2026-11-13T10:38:01.755Z after the live browser API response was parsed and saved. The initial standalone public-network attempts timed out; the browser-rendered Overpass JSON supplied this first snapshot. Government review dates remain date-only 2026-11-13. Counts change with future successful updates and do not imply exhaustive coverage.
